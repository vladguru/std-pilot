# Архитектура

Стадия 2 (п. 3, 8, 10, 11 спеки). Архитектуру решает агент (п. 2 спеки): владельцу уходят только вопросы по безопасности, составу персональных данных и новым внешним сервисам. Вопросы — по `.agents/skills/std-ask/SKILL.md`.

## Когда применять

`SPEC.md` согласован (статус «согласовано ДД.ММ.ГГГГ»); для проектов с интерфейсом выбрано визуальное направление (`std-design`).

## Шаги

1. **Прочитай** `SPEC.md`, `docs/overview.md`, `docs/decisions.md`, профиль `AGENTS.md`.
2. **Технологии.** Возьми стек по умолчанию: бэкенд Go + PostgreSQL (Python — для машинного обучения, данных, ИИ и библиотек только для Python); интерфейс TypeScript + React (Next.js) + Tailwind CSS + shadcn/ui; контракт API — OpenAPI. Отступление допустимо с записью Р-NN: что выбрано, почему, альтернативы. Новый платный или внешний сервис — вопрос владельцу.
3. **Составь `ARCHITECTURE.md`** по шаблону проекта:
   - схема контекста и схема контейнеров (сервисы, интерфейс, БД, очереди, протоколы);
   - схема компонентов для сложных сервисов;
   - схемы последовательностей для каждой интеграции и ключевого сценария, включая ошибки и повторы;
   - схема состояний для сущностей со статусами;
   - слои и правила зависимостей (предметный, прикладной, транспортный, хранение);
   - инварианты, каждый проверяется тестом;
   - пороги производительности для проектов с интерфейсом.
   Схемы — Mermaid, с подписью и легендой; отрендери и проверь изображение.
4. **Модель угроз** в `docs/dev/` (модель безопасности): активы, границы доверия, потоки данных, перечень персональных данных и сроки хранения, матрица «роль × действие», меры. Состав персональных данных и права доступа — решение владельца: вынеси вопросом.
5. **Правило переносимости** — обязательный раздел `ARCHITECTURE.md`: у каждого сервиса `Dockerfile`; вся система запускается `docker compose up` из `deploy/`; настройки только из переменных окружения; код, привязанный к платформе, запрещён, кроме тонкого адаптера с записью Р-NN; миграции БД применяются самим сервисом либо отдельной командой из `docker-compose.yml`.
6. **Эксплуатационная готовность:** эндпоинты `/healthz` и `/readyz`; журналы в структурированном виде без секретов и персональных данных; аутентификация только проверенными готовыми решениями; резервное копирование и проверенное восстановление для БД.
7. **Структура проекта** — по п. 3 спеки: монорепозиторий, обязательная структура корня и `docs/`; внутри сервиса — шаблон стека, отступление с Р-NN.
8. **PR.** Открой PR с `ARCHITECTURE.md`, моделью угроз и Р-NN. Если PR затрагивает ограничители или состав персональных данных — метка `на-согласовании`. Далее — `std-plan`, затем контрольная точка 2 (`std-gate`).

## Результат

`ARCHITECTURE.md` со схемами и разделом переносимости, модель угроз, записи Р-NN по технологиям; вопросы владельцу по безопасности.

## Стоп-условия и эскалация

- Состав персональных данных, права доступа, платёжные сценарии без ответа в `SPEC.md` — вопрос владельцу, затронутые разделы не проектируй «наугад».
- Платформо-зависимое решение допустимо только тонким адаптером с Р-NN.
- Не принимай решение, которое делает проект непереносимым на хост с Docker.

## Модель и уровень

Работу выполняет субагент Claude `std-architect` (Opus 5.5, xhigh). Если ты — субагент `std-architect`, выполняй сам. Параметры вызова Codex — `.agents/codex-runs.json`, запись `std-architect`.
