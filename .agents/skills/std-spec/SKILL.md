# Техническое задание

Стадия 1 (п. 3, 4, 6 спеки). Ты составляешь требования, владелец их согласует. Формат — шаблон `SPEC.md` проекта; вопросы владельцу — по `.agents/skills/std-ask/SKILL.md`.

## Когда применять

Есть бриф (`std-discover`) или запрос на изменение требований. Любое изменение `SPEC.md` — тоже сюда: правка требований не делается мимо согласования.

## Шаги

1. **Источники.** Бриф (`docs/overview.md`), отвеченные вопросы, `docs/decisions.md`, текущий `SPEC.md`.
2. **Требования.** Каждое — с идентификатором `ТР-NN` (не меняется и не используется повторно), приоритетом и формулировкой на языке бизнеса. Одно требование — одна проверяемая мысль.
3. **Критерии приёмки.** Для каждого требования — `AC-NN` в форме «дано / когда / тогда» со ссылкой на требование. Критерий проверяем автоматическим тестом: без неопределённых слов («быстро», «удобно», «и т. п.»), с конкретными значениями.
4. **Ошибки и крайние случаи.** Для каждого сценария опиши, что происходит при неверных данных, отсутствии прав, пустом результате, повторе действия, отказе внешней системы, большом объёме.
5. **Не входит в объём.** Перечисли явно, что исключено; это защита от расползания задания.
6. **Критичные функции.** Предложи перечень идентификаторов требований для состязательных тестов и приёмочных тестов от другого производителя отдельным разделом `SPEC.md` «Критичные функции (предложение)»; строку профиля «Критичные функции» меняет отдельный PR после согласования (изменение профиля — ограничитель).
7. **Самопроверка.** Противоречия между требованиями; требования без AC; AC без требования; неоднозначные слова; неописанные ошибки. Неясность в бизнес-области — вопрос владельцу (`std-ask`), а не догадка: если у вопроса есть умолчание, запиши требования и AC по рекомендованному варианту и пометь их «ожидает ответа В-NN»; если умолчания нет, внеси требование без AC с пометкой «ожидает ответа В-NN» и выдели такие разделы отдельным списком. Метка `стоп` здесь не ставится (заданий ещё нет): статус виден в `SPEC.md` и в описании PR.
8. **PR.** Статус в файле — «черновик». Ветка `docs/spec-<кратко>`. Открой PR с меткой `на-согласовании`: владелец одобряет его кнопкой Approve или комментарием «согласовано». Проверь одобрение по справочнику GitHub («Одобрение владельца») и слей PR с проверкой головного коммита. Затем отдельным PR, меняющим только строку статуса, замени статус на «согласовано ДД.ММ.ГГГГ» со ссылкой на одобрение; после этого задания могут опираться на AC. Без одобрения владельца PR с требованиями не сливается.
9. **Проверка.** Запроси быструю проверку Codex на противоречия с остальным ТЗ по записи `std-review` (`.agents/skills/std-review/SKILL.md`; запись `std-spec` в `.agents/codex-runs.json` нужна только для запуска самого `std-spec` в Codex); для контрольной точки 1 — полное ревью (`std-gate`).

Объёмное ТЗ допускается размещать в `docs/`; тогда `SPEC.md` служит указателем на него.

## Результат

`SPEC.md` со статусом «черновик» в PR с меткой `на-согласовании`; список вопросов владельцу; после одобрения — «согласовано ДД.ММ.ГГГГ».

## Стоп-условия и эскалация

- Противоречие в требованиях, неясность в бизнес-области, вопросы безопасности и персональных данных — вопрос владельцу; без умолчания, работа по затронутому разделу стоит.
- Не меняй согласованные требования и AC без нового PR на согласование; не добавляй требования, которых владелец не подтверждал.
- Технические решения (стек, структура) в ТЗ не фиксируй: это `std-architect`.

## Модель и уровень

Работу выполняет субагент Claude `std-spec` (Opus 5.5, xhigh). Если ты — субагент `std-spec`, выполняй сам. Параметры вызова Codex — `.agents/codex-runs.json`, запись `std-spec`.
