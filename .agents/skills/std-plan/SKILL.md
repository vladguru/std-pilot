# Декомпозиция и карточки

Стадия 2 и ступень 3 лестницы эскалации (п. 4.2 спеки). Тяжёлая модель думает, лёгкая выполняет: карточка составляется так, чтобы исполнителю не пришлось принимать архитектурных решений. Из `.agents/skills/writing-plans/SKILL.md` бери идеи — точные сигнатуры, имена тестов, раздел «фокус ревью» (входы, о которых ТЗ молчит, с тестом в карточке-владельце); формат плана superpowers (шаги с коммитами, сохранение в `docs/superpowers/`, выбор способа выполнения) не используется. Поправки стандарта — `.agents/skills/std-task/references/superpowers.md`. Команды GitHub — в `.agents/skills/std-ask/references/github.md`.

## Когда применять

Есть согласованное ТЗ и `ARCHITECTURE.md`; либо `std-task` или `std-run` просят уточнить карточку (эскалация, ступень 3) или пересмотреть план модуля после трёх эскалаций.

## Шаги

1. **Поставки.** Сгруппируй работу в поставки (milestone) — законченные наборы функций, которые принимает владелец; 1–2 на проект.
2. **Каркас.** Если в проекте нет `Makefile` с целями `ci`, `test`, `lint`, CI и линтеров, первая карточка создаёт их по шаблонам стека. Это первое появление ограничителей: PR каркаса идёт с меткой `на-согласовании`, а владелец отвечает на один вопрос (`std-ask`); остальные карточки от него зависят.
2. **Образцы.** Первый экземпляр каждого шаблона — первый эндпоинт целиком, первый экран, первая миграция, первый интеграционный тест — оформи отдельным заданием для тяжёлой модели (`std-task-heavy`). Остальные экземпляры — задания лёгким моделям «по образцу».
3. **Карточки.** Каждое задание — issue с меткой `задание` в своём milestone. Содержание карточки:
   - файлы и модули, которые изменяются, и те, которые изменять нельзя;
   - сигнатуры функций и интерфейсы на границах модулей;
   - AC (`AC-NN`) и имена тестов, которые нужно написать;
   - инварианты и ссылки на разделы `ARCHITECTURE.md`;
   - образец: «выполнить по примеру `<путь>`»;
   - критерий готовности и ориентир объёма;
   - строка «Исполнитель»: `std-task`, `std-task-high` или `std-task-heavy` (образец); допустимые зависимости (пакеты) перечисли в карточке — устанавливает их окружение, а не исполнитель.
4. **Лимит.** Объём карточки — в пределах значения «Лимит задания» профиля (прикладной код без тестов). Больше — дроби. Неделимое задание — признак того, что нужно решение владельца или пересмотр архитектуры (стоп-условие `std-run`).
5. **Зависимости.** Укажи, какие задания должны быть закрыты раньше; порядок — по зависимостям. Циклов быть не должно. Сначала создай issue, затем впиши в тела карточек реальные номера зависимостей.
6. **Критичные функции.** Для требований из строки профиля «Критичные функции» добавь карточку «приёмочные тесты по AC» (уровень 11 п. 6.3): тесты по AC до кода пишет Codex (запись `std-task` в `.agents/codex-runs.json`), карточки реализации зависят от неё.
7. **Тесты и документы.** В каждую карточку включи тесты, обновление документов и схем в том же PR (`std-docs`); для интерфейса — токены и компоненты по `std-design`.
8. **Самопроверка.** Для каждой карточки: исполнитель-лёгкая-модель не ищет по репозиторию, не выбирает архитектуру, знает, когда закончено. Все AC согласованного `SPEC.md` покрыты карточками; ни одно задание не меняет ограничители без вопроса владельцу.

## Уточнение при эскалации

Если карточку вернули (ступень 3): прочитай комментарии «Эскалация:» в задании (оно помечено `эскалация`), найди пробел (нет сигнатуры, неверная зависимость, слишком большой объём), уточни карточку или раздроби её. Задание возвращается на ступень 1. Если после уточнения оно неделимо и не выполняется — ступень 4 (`std-task-heavy`).

## Результат

Milestone с карточками-заданиями, образцы шаблонов, граф зависимостей; список вопросов владельцу, если они возникли.

## Стоп-условия и эскалация

- Разбить на части в пределах лимита нельзя — вопрос владельцу или пересмотр `ARCHITECTURE.md`.
- Карточка требует решения по бизнесу или безопасности — `std-ask`: неясность в бизнес-области профиля без ответа в `SPEC.md` и `docs/decisions.md` — не повод выбрать умолчание, а стоп-условие `std-run`: карточка получает метку `стоп`, остальные идут. Технические решения принимай сам и записывай Р-NN.
- Карточка зависит от решения владельца (например, выбор стиля) — метка `стоп` и пометка в зависимостях.
- Самодостаточность карточек проверяется на контрольной точке 2 (`std-gate`); замечания оформляются заданиями milestone «Исправления поставки N».

## Модель и уровень

Работу выполняет субагент Claude `std-plan` (Opus 5.5, high). Если ты — субагент `std-plan`, выполняй сам. Параметры вызова Codex — `.agents/codex-runs.json`, запись `std-plan`.
