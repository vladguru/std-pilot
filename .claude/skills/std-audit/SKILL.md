# Аудит репозитория

Уровень 12 п. 6.3 спеки: контрольные точки 3–5. Ведёт тяжёлая модель; проверка Codex на GPT-6 Astra даёт взгляд другого производителя. Команды GitHub — в `.agents/skills/std-ask/references/github.md`.

## Когда применять

По вызову `std-gate`. На контрольной точке 5 аудит охватывает весь репозиторий и комплект документов.

## Шаги

1. **Эталон.** `ARCHITECTURE.md`, `SPEC.md`, `docs/glossary.md`, профиль `AGENTS.md`.
2. **Архитектурный дрейф:** нарушены ли слои и правила зависимостей, инварианты, правило переносимости; расходятся ли схемы с кодом.
3. **Дублирование и неиспользуемый код:** повторы логики, мёртвые функции и зависимости, не удалённые временные решения.
4. **Технический долг:** упрощения и их причины, недоделанное, пропущенные и нестабильные тесты, подавления линтера без обоснования; обнови `docs/dev/` (технический долг и ограничения).
5. **Эскалации:** посчитай по комментариям «Эскалация:» в заданиях поставки долю эскалаций по модулям за поставку. Три и более в одном модуле — признак слабой карточки или архитектуры; предложи пересмотр плана модуля (`std-plan`).
6. **Вызов Codex.** Параллельный аудит — по записи `std-audit` из `.agents/codex-runs.json` на собственном исполнителе (Р-44); объедини результаты.
7. **Оформи замечания** с уровнями «критично / важно / незначительно» issue в milestone «Исправления поставки N».

## Результат

Перечень замечаний аудита, обновлённый `docs/dev/` (технический долг), раздел «Аудит» отчёта контрольной точки.

## Стоп-условия и эскалация

- Аудит ничего не исправляет и не удаляет: удаление мёртвого кода — отдельное задание.
- Признаки нарушения безопасности передавай `std-security`.
- Решения по ограничителям и бизнес-требованиям — вопрос владельцу (`std-ask`).

## Модель и уровень

Работу выполняет субагент Claude `std-audit` (Opus 5.5, xhigh). Если ты — субагент `std-audit`, выполняй сам. Параметры вызова Codex — `.agents/codex-runs.json`, запись `std-audit` (GPT-6 Astra, xhigh).
