# Порядок работы с репозиторием

Документ описывает ветки, коммиты, PR, ревью, слияние и метки. Требования и архитектура описаны в `SPEC.md` и `ARCHITECTURE.md`.

## Ветки

- Основная ветка — `main`. Изменения попадают в неё только через PR.
- Ветка задания создаётся от актуального `main` и называется `<тип>/<номер issue>-<кратко>`, например `feat/42-export-orders`.
- Переписывать историю, использовать `--force` и удалять теги запрещено.
- Принятая версия отмечается тегом `vN`, кандидат на контрольной точке — тегом `rc-N`.

## Коммиты

Сообщения коммитов оформляются по Conventional Commits: `<тип>: <что сделано>`.

| Тип | Назначение |
|---|---|
| `feat` | Новая функция |
| `fix` | Исправление ошибки |
| `docs` | Документация и схемы |
| `test` | Тесты |
| `refactor` | Изменение кода без изменения поведения |
| `chore` | Служебные изменения: зависимости, настройки |
| `ci` | Проверки CI |

Каждый коммит содержит служебные строки с моделью и скиллом, которыми он создан:

```
Model: claude-sonnet-5-5
Skill: std-task
```

## PR

- Один PR — одно задание. Объём — в пределах лимита задания из профиля в `AGENTS.md`.
- PR ссылается на issue задания (`Closes #42`).
- Описание PR — отчёт по заданию: что сделано; требование → код → тест; доказательства проверки (выполненные команды и их вывод, вывод падающего теста до исправления); объём; решения Р-NN; вопросы В-NN; замеченное вне задания.
- Документы и схемы обновляются в том же PR. PR, изменяющий код приложений и сервисов без изменений в `docs/`, получает метку `без-документов` с обоснованием.

## Ревью

- Каждый PR проходит CI, самопроверку автора и автоматическое ревью Codex в лёгком режиме: только замечания уровней «критично» и «важно».
- Слияние блокирует только замечание уровня «критично». Несогласие автора с критичным замечанием решает третье мнение (`std-arbiter`); вопросы бизнеса и безопасности передаются владельцу.
- PR, изменяющий `SPEC.md`, дополнительно проверяется на противоречия с остальным ТЗ и согласуется владельцем.

## Контрольные точки

Полное перекрёстное ревью проводится 3–5 раз за проект.

| № | Контрольная точка | Проверяемый объём |
|---|---|---|
| 1 | ТЗ и визуальное направление | `SPEC.md`, варианты стиля |
| 2 | Архитектура и план | `ARCHITECTURE.md`, модель угроз, схемы, токены и компоненты, карточки и образцы |
| 3–4 | Поставка | Все изменения с предыдущей принятой версии |
| 5 | Передача | Весь репозиторий и комплект документов |

Замечания контрольной точки оформляются issue в milestone «Исправления поставки N». Отчёт сохраняется в `docs/reports/`.

## Слияние

PR сливается, если:

- CI выполнен успешно;
- нет замечаний уровня «критично»;
- для PR с меткой `на-согласовании` получено одобрение владельца.

Issue задания закрывается слиянием.

## Метки

| Метка | Назначение |
|---|---|
| `задание` | Issue с заданием: содержание, требования и AC, ориентир объёма, зависимости |
| `нужен-ответ` | Вопрос владельцу (скилл `std-ask`) |
| `на-согласовании` | PR, который сливается только после одобрения владельца: изменения `SPEC.md`, визуального направления, состава персональных данных, ограничителей |
| `стоп` | Задание остановлено; причина — в комментарии |
| `пауза` | Все работы останавливаются в ближайшей безопасной точке |
| `эскалация` | Задание переведено на следующую ступень лестницы эскалации |
| `без-документов` | PR изменяет код без изменения документов; обоснование — в описании PR |
